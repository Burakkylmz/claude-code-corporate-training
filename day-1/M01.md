# M01 — Agentic Working Model

## Learning Goal

Claude Code'un unfamiliar bir repository üzerinde önce gözlem yapıp working map oluşturmasını, sonra focused investigation'a geçmesini görmek.

## Key Idea

```text
Model + Repository Context + Tools + Execution + Observation + Iteration
```

> **Agentic ≠ Autonomous**

## D01-M01-P01 — Repository Discovery

### Mode

```text
Plan Mode
```

### Prompt

```text
Bu repository'yi high-level seviyede keşfet.

Amacım henüz bir feature geliştirmek veya problem çözmek değil.
Önce repository için bir working map oluşturmak istiyorum.

Şunları belirle:

1. Main source ve test dizinleri
2. Build system
3. Runtime / framework
4. Ana configuration dosyaları
5. Project-level instruction dosyaları
6. Ana application entry point
7. High-level package/module yapısı

Her finding için mümkün olduğunca evidence göster.

Ayrıca şu ayrımı koru:

- Evidence: doğrudan repository'de gözlemlediğin bilgi
- Inference: mevcut evidence'dan çıkardığın ama doğrudan doğrulanmamış sonuç

Bu aşamada:

- file değiştirme,
- file oluşturma,
- build/test çalıştırma,
- dependency yükleme,
- Git mutation yapma.

Sadece repository discovery yap.

Açıklamalarını Türkçe yap.
File/path, class/method, command ve software engineering terminology'yi English bırak.
```

### What to Observe

- Hangi tools kullanıldı?
- `CLAUDE.md` ve `.claude/rules/*` fark edildi mi?
- Evidence ve inference ayrıldı mı?
- Repository state değişti mi?

### Discussion Point

```text
Evidence ≠ Inference
```

### Verification

```powershell
git status --short
```

Expected:

```text
<empty>
```

## D01-M01-P02 — Architecture Discovery

### Mode

Aynı session, `Plan Mode`. `/clear` yapma.

### Prompt

```text
Önceki repository discovery sonucunu kullan.

Şimdi repository'nin high-level application architecture'ını keşfet.

Özellikle şu flow'u trace et:

HTTP request
→ controller
→ application/orchestration layer
→ gateway/port interfaces
→ adapter implementations

Şunları belirle:

1. Ana HTTP endpoint/controller
2. Controller'ın çağırdığı application/service class
3. Application service'in dependencies'i
4. Port/gateway interface'leri
5. Concrete adapter implementations
6. Dependency direction
7. Spring dependency injection / component wiring
8. Configuration binding varsa ilgili yapı

Her finding için source evidence kullan.

Doğrudan gözlemlemediğin behavior'ı kesinmiş gibi yazma.
Evidence ve inference ayrımını koru.

Bu aşamada:
- implementation yapma,
- file değiştirme,
- test/build çalıştırma,
- Git işlemi yapma.

Açıklamalarını Türkçe yap.
Code identifier ve software engineering terminology English kalabilir.
```

### What to Observe

- `CallController → CallOrchestrationService` flow'u görülebiliyor mu?
- Application service concrete adapters yerine gateway interfaces'e mi depend ediyor?
- Spring wiring evidence ile mi açıklanıyor?

### Discussion Point

```text
Working map
→ deeper source evidence
→ validated architecture model
```

## D01-M01-P03 — Focused CRM Investigation

### Prompt

```text
Şimdi yalnızca CRM timeout behavior'ını incele.

Henüz çözüm veya implementation planı üretme.

Şunları araştır:

1. CRM timeout nasıl tetikleniyor?
2. Exception hangi class/package içinde oluşuyor?
3. Exception CallOrchestrationService üzerinden nasıl propagate ediyor?
4. Timeout sonrasında Bot, IVR ve Notification çağrıları devam ediyor mu?
5. Bu davranışı hangi testler doğruluyor?
6. Hangi behavior source code'dan implied ama testlerle explicit olarak korunmuyor?
7. Documentation ile mevcut code arasında fark var mı?
8. Bu behavior'ı değiştirmek gerekirse minimum relevant change surface hangi alanlarda olabilir?
9. Hangi sorular implementation başlamadan önce açık kalıyor?

Code + Tests + Docs evidence kullan.

Henüz:
- solution önerme,
- implementation planı oluşturma,
- file değiştirme,
- test/build çalıştırma,
- Git işlemi yapma.

Açıklamalarını Türkçe yap.
```

### What to Observe

- `CRM-TIMEOUT*` synthetic trigger
- `CrmTimeoutException` propagation path
- downstream calls'ın timeout sonrasında çalışıp çalışmaması
- code + tests + docs triangulation

### Discussion Point

> **Behavior implied by code ≠ behavior explicitly protected by tests.**
