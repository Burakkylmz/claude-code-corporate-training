# M03 — Context Engineering

## Learning Goal

Agent'ın karar kalitesini yalnızca "daha fazla context" ile değil, doğru ve yeterli context seçimiyle iyileştirmek.

## Key Idea

```text
Relevant
+ Correct
+ Fresh
+ Consistent
→ Better Context
```

> **More Context ≠ Better Context**

## D01-M03-P01 — Minimum Sufficient Context

### Mode

```text
Plan Mode
```

### Prompt

```text
Yeni requirement:

CRM timeout olduğunda request başarısız olmak yerine
UNKNOWN customer segment ile routing'e devam etmeli.

Henüz solution veya implementation planı oluşturma.

Önce yalnızca bu requirement için minimum sufficient context'i belirle.

Şunları çıkar:

1. Gerekli requirement/documentation context
2. Gerekli production code
3. Gerekli tests
4. Gerekli architecture/project instructions
5. Security/governance açısından ilgili context
6. Kararı etkilemeyecek irrelevant context
7. Context gaps
8. Conflicting information
9. Human clarification gerektiren sorular

Repository'nin tamamını broad şekilde tarama.

Narrow concern → narrow scope yaklaşımını kullan.

Henüz:
- solution önerme,
- implementation planı üretme,
- file değiştirme,
- build/test çalıştırma,
- Git işlemi yapma.
```

### What to Observe

- requirement document
- relevant application/service code
- gateway/port boundary
- relevant adapter behavior
- relevant tests
- `CLAUDE.md`
- `.claude/rules/*`
- architecture documentation

### Discussion Point

> **Minimum sufficient context ≠ minimum file count.**

> **Subagent isolation useful ≠ every exploration needs subagents.**

## D01-M03-P02 — Rule-aware Planning

### Prompt

```text
Önceki context-scoping çalışmasındaki minimum sufficient context'i kullan.

CRM timeout → UNKNOWN requirement'ı için yalnızca planning analysis yap.

Önce:

## Baseline Technical Approach

Sadece requirement + mevcut code behavior'a bakıldığında
bir developer'ın düşünebileceği en doğrudan teknik yaklaşımı göster.

Bu implementation recommendation değildir.

Sonra:

## Rule-Aware Engineering Plan

Şu context ile aynı yaklaşımı yeniden değerlendir:

- CLAUDE.md
- .claude/rules/*
- docs/architecture.md
- docs/exercises/day-2-crm-timeout.md
- ilgili production code
- ilgili tests

Özellikle değerlendir:

1. Baseline approach project rules ile uyumlu mu?
2. Application layer'ın crm.adapter.CrmTimeoutException'a dependency alması uygun mu?
3. Gateway contract timeout failure semantics'i nasıl ifade ediyor?
4. Existing baselinePropagatesCrmTimeout testi nasıl ele alınmalı?
5. Minimum change surface nedir?
6. Hangi decisions human approval gerektiriyor?

Her karar için:

- Decision
- Evidence
- Relevant Rule / Constraint
- Planning Impact

Ayrıca:

| Baseline Decision | Project Rule / Architecture Constraint | Rule-Aware Change |

tablosu oluştur.

Henüz implementation yapma.
```

### Discussion Point

> **Context bazı solution'ları geçersiz hale getirebilir.**

## D01-M03-P03 — Human Architecture Constraint

```text
Human architecture decision:

CallOrchestrationService'in crm.adapter package'ındaki
herhangi bir concrete type'a dependency almasına izin vermiyorum.

Architecture constraint:

application
→ port / domain abstractions

application
↛ concrete adapter implementation details

Bu constraint minimum file count hedefinden daha önceliklidir.

Önceki planı bu constraint altında revise et.

Henüz implementation yapma.
```

## D01-M03-P04 — Final Human Decisions

```text
Human decisions:

1. CrmTimeoutException crm.port package'ına taşınacak.
2. RuntimeException olarak kalacak.
3. Explicit throws clause eklenmeyecek.
4. Failure semantics Javadoc ile belirtilecek.
5. Non-timeout exception test'i MockCrmGateway'e yeni fixture eklemeden
   Mockito ile service test seviyesinde doğrulanacak.
6. README/docs bu rehearsal kapsamında değiştirilmeyecek.

Bu kararlarla planı final hale getir.

Henüz implementation yapma.
```

### Discussion Point

> **Minimal change ≠ fewest files.**

## Module Takeaway

> **Context engineering, modele daha fazla token vermek değildir. Karar alanını doğru evidence, rules ve human constraints ile daraltmaktır.**
