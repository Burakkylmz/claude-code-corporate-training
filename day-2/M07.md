# M07 — Testing, Debugging & Safe Refactoring

## Learning Goal

Yeni bir engineering task'ını planlayıp kapattıktan sonra ortaya çıkan regression/failure'ı evidence → hypothesis → root cause → minimal fix zinciriyle debug etmek ve behavior baseline korunduktan sonra ayrı bir safe refactor yürütmek.

## Key Idea

```text
Task
→ Plan
→ Execute
→ Verify
→ Close

Then:

Regression
→ Reproduce
→ Evidence
→ Hypothesis
→ Root Cause
→ Minimal Fix
→ Regression Verification
→ Separate Refactor
```

## D02-M07-P01 — New Task: Fallback Audit Notification

### Mode

```text
Plan Mode
```

### Prompt

```text
Engineering Ticket: CC-202 — CRM Fallback Audit Notification

Repository:
call-center-integration-platform

Context:
CC-201 ile CRM timeout fallback behavior'ı implement edildi ve human review ile kabul edildi.

New requirement:
CRM timeout fallback gerçekleştiğinde sistem, repository'de mevcut bir
Notification abstraction/port varsa bunu kullanarak fallback occurrence için
internal audit/notification signal üretmeli.

Constraints:

- önce mevcut notification abstraction gerçekten var mı evidence ile doğrula
- yoksa yeni external contract uydurma; BLOCKED olarak raporla
- successful CRM flow değişmemeli
- fallback routing notification sonucuna bağımlı hale getirilmemeli
- existing public/external API requirement olmadan değişmemeli
- new dependency eklenmemeli
- unrelated refactor yapılmamalı

Repository-wide exploration yapma.
Yalnız ticket için gereken surface'i incele.

Henüz edit yapma.

Extensive plan üret:

1. Current relevant flow
2. Confirmed notification boundary
3. Acceptance criteria
4. Exact change surface
5. Ordered implementation steps
6. Failure semantics
7. Test matrix
8. Verification commands
9. Risks / assumptions
10. Stop conditions

Plan sonunda:
READY FOR HUMAN REVIEW
veya
BLOCKED BY MISSING EVIDENCE
```

### What to Observe

- Claude “notification var” diye varsayıyor mu, gerçekten doğruluyor mu?
- Task planı fallback flow'u notification'a yanlışlıkla couple ediyor mu?
- Failure semantics planın içinde açık mı?

## D02-M07-P03 — QA Regression: Reproduce Before Fix

### Mode

```text
Default Mode
```

### Scenario

```text
QA Bug Report: BUG-203

CRM timeout fallback sonrasında notification collaborator exception üretirse
call routing beklenmedik şekilde fail ediyor.

Expected:
Notification side-effect failure, confirmed architecture semantics'e göre
fallback routing sonucunu bozmamalı.

Actual:
QA fallback routing'in tamamlanmadığını raporluyor.
```

> Instructor note: Bu bug current implementation'da doğal olarak oluşmuyorsa, demo branch'inde notification call'ını routing result'tan önce ve exception handling olmadan çalıştıran küçük bir regression seed'i hazırlayın. Öğrencilere root cause'u söylemeyin; yalnız QA symptom'unu verin.

### Prompt

```text
BUG-203 raporlandı.

Hemen fix yapma.
Önce failure'ı reproduce et.

1. Existing relevant tests'i oku.
2. Expected vs actual behavior'ı netleştir.
3. Deterministic failing test veya mevcut failing evidence ile symptom'u reproduce et.
4. Exact assertion/exception'ı raporla.
5. Relevant stack-trace frames'i göster.
6. Root cause söylemeden önce en fazla 3 testable hypothesis üret.
7. Her hypothesis için minimum confirming/rejecting evidence yaz.

Production code'u değiştirme.
Testi passing yapmak için assertion zayıflatma.

Failure reproduce edilemiyorsa STOP ve bunu raporla.
```

### What to Observe

- Agent symptom → edit refleksine giriyor mu?
- Failing test gerçekten bug behavior'ını kanıtlıyor mu?
- Hypothesis ile root cause birbirine karıştırılıyor mu?

### Discussion Point

> **A bug report is a symptom. A failing reproducible case is evidence.**

## D02-M07-P04 — Root Cause → Minimal Fix

### Prompt

```text
BUG-203 artık deterministic olarak reproduce ediliyor.

Failure evidence'a dayanarak root cause analysis yap.

Çıktı:

## Evidence
## Candidate Hypotheses
## Confirmed Root Cause
## Exact File / Method
## Minimal Fix Plan
## Explicit Non-Changes
## Tests to Re-run
## Regression Risk

Root cause evidence ile doğrulanmadan edit yapma.

Human approval sonrasında yalnız confirmed root-cause surface için minimal fix uygula.

Not allowed:
- unrelated cleanup
- broad exception swallowing
- test weakening
- dependency change
- architecture rewrite
- commit/push

Fix sonrası önce failing targeted test'i çalıştır.
Green ise relevant regression tests'i çalıştır.

Sonuçları ve git diff'i raporla.
```

### What to Observe

- Root cause bir stack frame üzerinden tahmin mi ediliyor, yoksa evidence ile doğrulanıyor mu?
- Fix minimum mu?
- Broad catch veya suppression gibi semantik olarak riskli çözüm kullanılıyor mu?

### Discussion Point

```text
Root-cause fix
≠
opportunistic cleanup
```

## D02-M07-P05 — Safe Refactoring as a Separate Change

### Mode

```text
Plan Mode → Human Approval → Edit
```

### Prompt

```text
BUG-203 minimal fix tamamlandı ve relevant regression tests green.

Şimdi code'da refactor opportunity olup olmadığını değerlendir.

Önce yalnızca candidate listesi üret:

- problem
- evidence
- expected maintainability benefit
- behavior risk
- change surface
- current requirement için gerekli mi?
- separate change olmalı mı?

Yalnız behavior-preserving ve küçük bir refactor gerçekten değer üretiyorsa
bir refactor planı öner.

Human approval olmadan refactor uygulama.

Onay verilirse:

- bug fix behavior'ını değiştirme
- public contract değiştirme
- test semantics'i zayıflatma
- refactor diff'ini bug-fix diff'inden conceptual olarak ayrı tut
- targeted + relevant regression suite'i yeniden çalıştır
- before/after complexity veya duplication farkını evidence ile açıkla

Sonunda:

REFactor ACCEPT / REVISE / REVERT recommendation üret.
Commit/push yapma.
```

### What to Observe

- Claude çalışan her code'u refactor etmeye çalışıyor mu?
- Refactor için measurable/observable benefit var mı?
- Behavior baseline testlerle korunuyor mu?
- Bug fix ile structural change zihinsel olarak ayrılıyor mu?

### Discussion Point

> **Refactoring, bug fix'in içine gizlenmiş cleanup değil; behavior baseline'dan sonra ayrı bir engineering decision'dır.**

## D02-M07-P06 — Final Task + Bug Closure

### Prompt

```text

Yeni edit yapma.

Rapor:

## CC-202
- acceptance criteria
- changed files
- verification evidence
- human review status

## BUG-203
- reproduced symptom
- confirmed root cause
- minimal fix
- regression evidence

## Refactor
- applied / not applied
- rationale
- verification evidence

## Final Repository State
- git status
- remaining risks
- known assumptions

Final statuslardan birini seç:
- READY FOR HUMAN ACCEPTANCE
- INCOMPLETE
- BLOCKED
```

### Discussion Point

```text
Feature delivery
+
Debugging discipline
+
Regression evidence
+
Optional safe refactor
=
engineering closure
```
