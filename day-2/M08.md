# M08 — Skills & Subagents

## Learning Goal

Main thread, Skill ve Subagent kullanımını görev tipine göre seçmek; subagent'ı context isolation için kullanırken usage overhead'ini de hesaba katmak.

## Key Idea

```text
Main Thread
→ sequential work with shared decisions

Skill
→ reusable specialized workflow

Subagent
→ isolated exploration / parallel investigation
```

---

## D02-M08-P01 — Classify the Work

### Mode

```text
Plan Mode
```

### Prompt

```text
Aşağıdaki engineering tasks'i execution mechanism açısından sınıflandır:

A. CallOrchestrationService'in tek method'unu okuyup 5 maddede özetlemek
B. Repository'de authentication flow'unun hangi file'larda olduğunu araştırmak
C. Her refactor sonrasında aynı verification checklist'ini uygulamak
D. İki bağımsız integration adapter'ını paralel olarak incelemek
E. Bir failing test'i root cause bulunana kadar sequential debug etmek

Her task için seç:

- Main Thread
- Skill
- Subagent
- Birden fazla mekanizma gerekiyorsa kombinasyon

Gerekçe olarak şunları değerlendir:

- context isolation
- sequential dependency
- repeatability
- parallelism
- usage/cost overhead
- need for human visibility

Henüz hiçbir task'ı execute etme.
```

### Discussion Point

> **Subagent kullanılabiliyor olması, kullanılması gerektiği anlamına gelmez.**

## D02-M08-P02 — Bounded Research Subagent

### Prompt

```text
Şu araştırma task'ı için yalnızca bir Explore-style subagent kullan:

"CRM integration boundary'de timeout behavior'ını etkileyen
production code ve tests hangi file'larda?"

Subagent'a dar scope ver:

- yalnız CRM boundary
- yalnız file/path + kısa relevance summary
- implementation yok
- edits yok
- tests/build yok
- Git yok

Main thread'e yalnızca:
- relevant files
- neden relevant oldukları
- açık evidence gaps

dönsün.

Subagent tamamlandıktan sonra main thread yeni action almasın.
```

### What to Observe

- Exploration detayları subagent context'inde mi kaldı?
- Main thread temiz bir summary mi aldı?
- Scope genişledi mi?

### Discussion Point

```text
Subagent isolation
→ main context benefit

but

Subagent requests
→ usage overhead
```

## D02-M08-P03 — When Not to Use a Subagent

### Prompt

```text
Şimdi şu task için subagent kullanma:

"CallOrchestrationService.route() method'unun current behavior'ını 5 maddede özetle."

Yalnızca minimum source file'ı oku ve sonucu ver.

Task sonunda:
- files read
- tools used
- subagents used

raporla.
```

### Discussion Point

> **Small bounded task için direct execution, subagent orchestration'dan daha verimli olabilir.**

## D02-M08-P04 — Create a Project-Scoped Exploration Subagent

### Mode

```text
Plan Mode
```

### Prompt

```text
call-center-integration-platform repository'si için project-scoped bir custom subagent oluştur.

Amaç:
Integration flow'larını implementation öncesinde araştırmak ve main thread'e
kanıta dayalı, bounded bir implementation plan döndürmek.

Subagent file:
.claude/agents/integration-flow-explorer.md

Subagent configuration:

- name: integration-flow-explorer
- description: Call orchestration ve CRM, Bot, IVR, Notification integration
  boundary'lerini change öncesinde araştırır; impacted files, tests, risks ve
  minimum implementation plan döndürür. Integration behavior değişikliklerinden
  önce proaktif olarak kullanılmalıdır.
- model: sonnet
- effort: medium
- maxTurns: 18
- permissionMode: plan
- tools:
  - Read
  - Grep
  - Glob
  - Bash
  - PowerShell

Subagent source code edit etmemeli.
Edit ve Write tool'larını verme.

Subagent system prompt'u şu davranışları zorunlu kılsın:

1. İlgili execution entry point'i bul.
2. Call orchestration flow'unu trace et.
3. Domain port/interface'leri belirle.
4. CRM, Bot, IVR ve Notification adapter boundary'lerini belirle.
5. Existing exception/fallback handling'i araştır.
6. İlgili tests'i bul.
7. Önemli her sonuç için exact file path ve symbol ver.
8. Evidence, Inference ve Unknown ayrımını açıkça yap.
9. Implementation yapma.

Output format:

## Current Flow
## Failure Path
## Impacted Files
## Implementation Plan
## Test Plan
## Risks

Ayrıca yalnız bu subagent aktifken Bash ve PowerShell command'larını kontrol eden
bir PreToolUse hook tanımla.

Hook file:
.claude/hooks/validate-readonly-command.ps1

PreToolUse matcher:
Bash|PowerShell

Hook behavior:

- stdin üzerinden hook JSON input'unu oku
- tool_input.command değerini incele
- read-only inspection command'larına izin ver
- git status ve git diff gibi read-only Git command'larına izin ver
- file mutation yapan shell command'larını block et
- git commit, push, reset, clean, checkout, switch, merge, rebase,
  cherry-pick ve restore gibi mutating Git command'larını block et
- blocked command için stderr'e açıklama yaz ve exit code 2 dön
- izin verilen command için exit code 0 dön

Bu aşamada application code, tests ve documentation değiştirme.
Yalnızca subagent definition ve ona ait hook'u oluştur.

İşlem sonunda:

- oluşturulan files
- subagent frontmatter
- allowed tools
- model
- permission mode
- PreToolUse behavior

özetini ver.
```

### What to Observe

- Subagent `.claude/agents/` altında project scope'ta mı oluşturuldu?
- `description`, delegation'ın ne zaman yapılacağını yeterince net anlatıyor mu?
- `model: sonnet` main thread modelinden bağımsız açıkça tanımlandı mı?
- Tool allowlist'te `Edit` veya `Write` var mı?
- `permissionMode: plan` exploration intent'i ile uyumlu mu?
- `maxTurns` bounded execution sağlıyor mu?
- `PreToolUse` yalnız Bash/PowerShell için scoped mu?
- Hook mutating command'ı tool execute edilmeden önce block ediyor mu?

### Discussion Point

```text
Prompt instruction
"Do not edit files"

        !=

Tool boundary + PreToolUse
"Prevent mutation"
```

> **Subagent prompt davranışı yönlendirir; tool scoping ve PreToolUse ise execution surface'i daraltır.**

## D02-M08-P05 — Explore the CRM Timeout Flow with the Custom Subagent

### Mode

```text
Plan Mode
```

### Prompt

```text
Yeni business requirement:

"CRM lookup sırasında CrmTimeoutException oluşursa incoming call hemen fail
olmamalı. Existing architecture kullanılarak call güvenli bir IVR fallback
path'ine yönlendirilmeli. Successful CRM flow değişmemeli."

Bu aşamada code edit etme.

Yalnızca integration-flow-explorer subagent'ını kullanarak repository'yi araştır.

Subagent aşağıdaki soruları evidence ile cevaplasın:

1. Incoming call için current execution path nedir?
2. CRM lookup hangi class/method üzerinden yapılıyor?
3. CrmTimeoutException gerçekten mevcut mu?
   - varsa nerede create/throw/translate/propagate ediliyor?
   - yoksa bunu açık bir evidence gap olarak raporla.
4. Existing IVR routing abstraction nedir?
5. Existing fallback/error-handling convention var mı?
6. Hangi production files change surface'e giriyor?
7. Hangi tests mevcut behavior'ı cover ediyor?
8. En küçük güvenli implementation plan nedir?

Subagent scope:

- repository exploration
- Read / Grep / Glob
- gerekirse yalnız read-only Bash veya PowerShell inspection commands
- git status / git diff gibi read-only Git inspection serbest
- implementation yok
- edits yok
- dependency ekleme yok
- build/test çalıştırma yok
- mutating Git yok

Main thread'e yalnızca şu structured summary dönsün:

## Current Flow
## Failure Path
## Impacted Files
## Implementation Plan
## Test Plan
## Risks
## Evidence Gaps

Her önemli conclusion için exact file path ve symbol belirt.
Evidence ile inference'i birbirine karıştırma.

Subagent tamamlandıktan sonra main thread hiçbir implementation action almasın.
Planı yalnızca human review için sun.
```

### What to Observe

- Main thread repository exploration detaylarıyla şişti mi?
- Subagent birden fazla package/file trace ederken kendi context'ini mi kullandı?
- Final summary exact file path ve symbol içeriyor mu?
- `CrmTimeoutException` veya IVR fallback hakkında unsupported assumption yaptı mı?
- Impacted files listesi bounded mı, yoksa gereksiz refactor scope'u açıldı mı?
- Implementation başlamadan önce human gate oluştu mu?

### Discussion Point

```text
Business Requirement
        ↓
Exploration Subagent
        ↓
Evidence
        ↓
Implementation Plan
        ↓
Human Review
```

> **Subagent'ın görevi burada code yazmak değil, main thread'in doğru code change'i yapabilmesi için uncertainty'yi azaltmaktır.**

## D02-M08-P06 — Main-Thread Editing After the Human Gate

### Mode

```text
Default Mode
```

### Prompt

```text
integration-flow-explorer tarafından üretilen exploration report ve
implementation plan human review'dan geçti ve onaylandı.

Şimdi implementation'ı main thread'de yap.
Bu task için implementation subagent kullanma.

Yalnızca approved exploration evidence'ına dayan.

Önce edit yapmadan önce şunları yaz:

1. Değiştirilecek exact files
2. Her file'ın neden değişeceği
3. Değiştirilmeyecek önemli boundary'ler
4. Expected behavioral change

Sonra minimum change ile requirement'ı implement et:

- successful CRM flow aynı kalmalı
- yalnız required CRM timeout scenario handle edilmeli
- existing IVR/domain abstraction mümkün olduğunca reuse edilmeli
- integration boundary'leri korunmalı
- unrelated refactor yapma
- yeni framework/dependency ekleme
- exception behavior'ını gereksiz genişletme
- focused tests ekle veya mevcut tests'i güncelle

Eğer exploration sırasında CrmTimeoutException'ın mevcut olmadığı veya requirement
ile repository'nin current behavior'ı arasında kritik bir mismatch olduğu
belirlenmişse bunu kendin invent ederek kapatma.
Implementation'ı durdur ve mismatch'i raporla.

Implementation tamamlandıktan sonra:

1. focused tests'i çalıştır
2. relevant full test suite'i çalıştır
3. git diff'i incele
4. changed files'i raporla
5. test results'i raporla
6. remaining risk veya uncertainty varsa açıkça belirt

Commit veya push yapma.
```

### What to Observe

- Main thread subagent'ın evidence'ını kullanarak mı karar verdi?
- Exploration tekrar baştan mı yapıldı, yoksa subagent summary'si yeterli oldu mu?
- Edit scope exploration plan ile uyumlu mu?
- Successful path korunuyor mu?
- Timeout handling doğru architectural boundary'de mi?
- Unrelated refactor oluştu mu?
- Tests yalnız happy path'i değil failure path'i de doğruluyor mu?
- Claude commit/push gibi user'ın istemediği Git actions'a geçti mi?

### Discussion Point

```text
Subagent
→ explore and reduce uncertainty

Main Thread
→ decide, edit, test, integrate
```

> **Exploration ile execution'ı ayırmak, main thread'deki sequential decision chain'i görünür ve denetlenebilir tutar.**

## D02-M08-P07 — Read-Only Verification with the Same Subagent

### Mode

```text
Plan Mode
```

### Prompt

```text
Implementation tamamlandı.

Şimdi integration-flow-explorer subagent'ını ikinci kez kullan.

Amaç:
Current git diff ve affected execution path üzerinden implementation'ı
read-only olarak verify etmek.

Hiçbir file değiştirme.
Hiçbir fix uygulama.
Commit veya push yapma.

Aşağıdaki criteria'yı tek tek kontrol et:

1. CRM timeout fallback business requirement karşılanıyor mu?
2. Successful CRM path korunmuş mu?
3. Existing IVR/domain abstraction reuse edilmiş mi?
4. Integration boundaries korunmuş mu?
5. Unnecessary coupling veya unrelated refactor oluşmuş mu?
6. Timeout behavior beklenenden daha geniş exception'ları swallow ediyor mu?
7. Focused tests failure path'i gerçekten doğruluyor mu?
8. Existing behavior için regression riski var mı?
9. Implementation approved plan ile uyumlu mu?

Her criterion için şu status'lardan yalnız birini kullan:

- PASS
- CONCERN
- FAIL

Her finding için:

- exact file path
- symbol/method
- evidence
- kısa rationale

ver.

Main thread'e yalnız verification report dönsün.
Subagent hiçbir code change yapmasın.
```

### What to Observe

- Aynı specialized subagent farklı lifecycle aşamasında tekrar kullanılabildi mi?
- Verification exploration'dan bağımsız ama aynı architectural lens ile yapıldı mı?
- `git diff` read-only inspection olarak kullanılabildi mi?
- PreToolUse hook mutating command denemelerini engelliyor mu?
- Report `PASS / CONCERN / FAIL` ile decision-ready hale geldi mi?
- Verification sırasında otomatik fix yapılmadı mı?

### Discussion Point

```text
Explore
  ↓
Plan
  ↓
Human Gate
  ↓
Edit in Main Thread
  ↓
Verify with Read-Only Subagent
```

> **Aynı subagent hem pre-change exploration hem post-change verification için kullanılabilir; önemli olan role boundary'nin değişmemesidir.**

---

## Extended Module Takeaway

```text
Use subagents to isolate exploration.

Bound their tools, model, scope and turns.

Use PreToolUse when a tool needs conditional enforcement.

Return evidence to the main thread.

Keep sequential implementation decisions visible.

Verify the final change with a read-only pass.
```



---

## Module Takeaway

```text
Use direct execution for tightly-coupled work.
Use Skills for reusable workflow.
Use Subagents for isolation.
Keep implementation ownership and human acceptance explicit.
```
